# UberClicker configuration app

One TypeScript frontend builds for the browser and the Tauri desktop companion.
Capacitor iOS/Android builds use that frontend too, with **Cue** remote
controls and secure destination storage. See [mobile builds and controls](mobile.md).
Both configure TX and RX directly over USB serial. **Configure devices** contains
the shared editor; **Receive cloud clicks** provides keyboard and OSC output in
the desktop build. The browser explains that receiving requires the desktop app.
Bluetooth is reserved for keyboard/MIDI output. Earlier experimental native mobile
builds and BLE configuration instructions do not apply to this firmware. See the
[user guide](user-guide.md) for device controls and the
[protocol contract](../contracts/config-protocol.md) for the serial wire format.

## Run and build

From the repository root:

```sh
npm ci --prefix app
npm test --prefix app
npm run dev --prefix app
```

Open the printed localhost URL in desktop Chrome or Edge. Hosted Web Serial needs
HTTPS. The app detects unavailable serial access and explains the fallback. Existing
Capacitor iOS/Android projects do not provide this desktop Web Serial transport;
their mobile role is sending cloud clicks to a destination computer.

For the desktop build, install Rust and Tauri's platform prerequisites, then run
`npm ci --prefix companion` and `npm run tauri --prefix companion dev` from the
repository root. `npm run tauri --prefix companion build` embeds the same
`app/dist` frontend. There is no separate companion frontend or Vite dependency.
The native bridge lists serial ports, opens a selected device at 115200 baud, and
feeds the shared protocol parser. Linux may require serial-device group permissions;
close other serial monitors before connecting.
The JSON schema validator is generated by `scripts/schema.mjs` before dev, test
and build, so both targets run static validation under Tauri's existing CSP.

Build the browser app and copy it to the website with:

```sh
node scripts/build-website.mjs
python3 -m http.server 8000 --bind 127.0.0.1 --directory website/dist
```

Open `http://127.0.0.1:8000/app/`. The generated app bundles are ignored by Git;
Pages rebuilds them from source during deployment. This command does not publish,
flash or connect to a device.

## Connect and edit

Connect a USB data cable to the TX or RX, then choose **Connect via USB serial**.
In the desktop app, open **Configure devices**, choose **Choose USB device**,
select the port and choose **Connect selected device**. Under **Cloud connection**,
**Use this computer’s room** pairs a TX directly to the companion's saved room;
create a destination in the web account dashboard, start its Pro trial/subscription, import its Companion code and pause receiver output first. Browser setup retains manual pairing.
Serial configuration is trusted at the physical connection: no Bluetooth chooser,
screen code, claim, app credentials or physical setup window is required. Connecting
and reading settings leaves cues running and the Bluetooth output host connected.
The firmware reports `ble_config:false`, `serial_config:true` and
`broadcast_radio:true`.

**Edit settings** starts a staged edit and pauses cues. **Apply changes** validates
the full draft, commits against its expected revision and rereads settings.
**Cancel** discards the draft. Either closes the edit and resumes normal output;
on-device menus and Bluetooth pairing can still pause cues. An edit expires after
two minutes without accepted progress. Disconnect attempts to cancel an idle edit;
unplugging or disconnecting during a request can leave it paused until expiry.

If Apply fails or times out, its outcome may be unknown. The app requires a fresh
read before presenting settings again and never retries Apply automatically.
Reconnect and reread before deciding whether to apply another change. Failed Cancel
also requires a reread. Reset is not required for ordinary reconnects.

## Settings

- **Role:** TX/RX firmware builds fix the device role. TX runs actions on button clicks.
  RX runs its own event actions for fresh cues from the TX selected with B1/B2.
- **Radio preset:** balanced or long range. TX and RX must use the same preset.
  RX sends no radio replies, and TX cannot confirm receiver delivery. There is no
  radio pairing wizard, receiver management or remote configuration.
- **Profiles and device name:** up to four profiles; choosing a profile makes it
  active when applied. Its name identifies the device on screen and, for TX, in
  RX discovery lists. Names allow 1–24 UTF-8 bytes. New devices default to their
  Bluetooth MAC's last four uppercase hex digits, such as `0A8F`. Advertising uses
  `UberClicker TX: 0A8F` or `UberClicker RX: 0A8F`; long Bluetooth names are shortened
  without splitting a character. Applying a rename preserves the output connection.
- **Actions:** each profile has separate Previous and Next event lists, with up to
  eight actions each. Add LoRa TX, BLE keyboard, BLE MIDI, OSC, UDP, TCP or Cloud TX
  for a paired companion room. Enable, duplicate, reorder or remove actions. Add multiple
  OSC actions to send to different destinations. Keyboard uses HID usage codes and modifier bits;
  named key dropdowns include arrows, Page Up/Page Down, Space, Enter, Escape,
  Backspace and P/N. Advanced keyboard mapping keeps custom HID usages and modifier
  bits available. MIDI offers note, CC and program messages, channels 1–16,
  numbers/values 0–127.
  OSC uses an address and one integer value (0–127); TCP appends LF. Each network action
  has its own destination hostname/IPv4 and port and uses the device’s Wi-Fi.
  LoRa TX is an explicit action; omit it for local-only events. See [outputs](outputs.md).
- **Wi-Fi:** Add or remove networks, each with its own SSID and explicit Keep / Replace / Clear password actions. Keep matches a saved SSID; renaming requires Replace or Clear. Clear supports open networks. The list is limited by device storage, not a fixed network count. Stored
  passwords are never read back. Wi-Fi supports network outputs and firmware updates;
  LAN configuration, mDNS and a setup hotspot are unavailable.

To pair an output host, open **Bluetooth pairing** on the device, select its displayed
name in the host OS and enter the passkey. Exit pairing to run cues. Serial editing
never opens this pairing window. Native USB HID/MIDI is unavailable on the stock
M5 serial connection.

## Firmware updates

Connect by serial and finish or cancel any edit, then choose **Open firmware update
screen**. The request only opens the on-device OTA screen; Check and Install require
physical button confirmation. See [installation and recovery](flashing.md).

## Checks and UI review

`npm test --prefix app` covers schema validation, UTF-8 limits, protocol framing,
serial correlation/stream cleanup, validate-before-Apply, stale revisions, uncertain
Apply and Cancel recovery, and update-screen gating. Legacy protocol tests retain
coverage for older paired-radio clients; those paths are absent from the current UI.
Firmware service/role tests run with `firmware/tests/config/run.sh`.

Preview URLs `?preview=home`, `?preview=edit`, `?preview=rx`, `?preview=osc` and
`?preview=midi` show labelled sample data. Fields and profile controls can be explored;
connection, Apply, Cancel and other hardware actions are disabled. Preview changes
never reach a device or persist. They are UI review tools, not hardware evidence.

Physical acceptance is still required for serial permissions/reconnect, Bluetooth
coexistence and renaming, radio discovery and selection, output delivery, power-loss
recovery and OTA. No hardware acceptance follows from a host build or preview.

The project MIT license is in `app/LICENSE`. Dependency notices ship in
`app/public/third-party-notices.txt` and `app/public/native-notices.txt`.

The current app requires schema-4 firmware; update both together. Firmware preserves existing schema-1/2 saved Wi-Fi credentials during migration.

## ProPresenter presentation mappings

In Companion's **Receive** view, pause output and enable **Use ProPresenter
presentation restrictions**. Enable Network in ProPresenter Settings, enter its
host IP and API port (default 50001), then **Fetch presentations**. Companion
reads all libraries using the [official ProPresenter API](https://openapi.propresenter.com/).

Add a transmitter, give it a name such as **Tx 1**, enter its 12-character device
ID, and select its allowed presentations (Ctrl / Cmd for multiple selections).
Repeat for **Tx 2**, then **Save mappings** and **Enable output**. Transmitter names
are labels; explicit selections use stable transmitter IDs and presentation UUIDs,
so identically named presentations remain distinct when selected individually. Assignments persist across restarts, and
fetching again preserves saved selections even if a presentation is missing.
With no selected presentations and no name rules, all presentations are blocked.

For example, assign presentations 1–3 to Tx 1 and 4–6 to Tx 2. Previous/Next only
works if the currently live presentation is assigned to the sending transmitter.
A click does not select a presentation or advance to another assigned presentation.
To learn a transmitter ID, enable ProPresenter mode with no assignments, press
its button, then pause output. The last transmitter ID appears below the mapping
list and prefills **Add transmitter**. The unassigned click is rejected.

ProPresenter mode replaces keyboard/OSC output for every transmitter; it never
falls back to those outputs when a click is blocked. Unknown transmitters, missing
live presentations, expired clicks and failed status requests cannot trigger a
slide. An uncertain trigger response pauses output and is never retried. Each
trigger names the authorized presentation UUID. If an operator switches the live
presentation between the status check and trigger, the API may return to that
assigned presentation; it cannot redirect the click to the new, unassigned one.

This requires the updated companion, relay and TX firmware. Older firmware still
works with ordinary keyboard/OSC mappings but has no transmitter ID for these
restrictions. Up to eight transmitters can share one room. Each uses the same room
pairing code and needs Cloud TX actions for Previous/Next. These assignments apply
to Companion output only; independently configured hardware actions are separate.

Each transmitter can also have **name rules**. Choose **Add name rule**, then
**Name contains** (case-insensitive, literal text such as `Sermon`) or **Name
matches regex** (such as `^Sunday (AM|PM)$`). Any selected presentation **or**
matching rule allows control. You can use rules alone without fetching or selecting
presentations. Rules check the live presentation name on every click, so newly
created presentations qualify immediately and renaming a presentation changes
whether its name matches. Explicit UUID selections remain allowed after a rename.

Regex is case-sensitive by default; use `(?i)^sermon` to ignore case. Enter patterns
without `/` delimiters. Matching searches anywhere in the name unless anchored
with `^` and `$`. The [Rust regex syntax](https://docs.rs/regex/latest/regex/#syntax)
supports groups, alternatives and character classes, but not lookaround or
backreferences. Blank/invalid patterns cannot be saved. Each transmitter supports
up to 16 rules of 512 UTF-8 bytes each, with a bounded compiled regex size. Missing
or blank live names never qualify via name rules. Existing UUID mappings are
preserved when upgrading.
